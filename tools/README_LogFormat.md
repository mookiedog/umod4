# Log File Format and Timing

The umod4 logfile format is primarily designed for space-efficiency since logs can be potentially huge (hundreds of megabytes).
The peak data rate for an engine running at redline is roughly 10K bytes per second.

## Log Construction

A log file represents a sequence of 'events' that were observed, then written to the filesystem.
In the umod4, events are generated by its three subsystems: the ECU, the EP, and the WP (which also reports the GPS data).

Events are represented by a sequence of one or more bytes in the logfile.
The first byte of an event is called the LOGID, and will always be present.
To save space, an event's length is not written to the log.
Instead, the header file [log_ids.h](../lib/inc/log_ids.h) defines each LOGID and the other symbols a decoder needs.
For each event in a logfile, the symbols in log_ids.h allow decoder software to determine:

* What each LOGID means
* For each LOGID, the number of additional data bytes contained in the event
* How to interpret that data (bool, float, a byte of raw sensor units, etc)

Log events from a single data source are guaranteed to be written in sequence.
For example, all ECU log events will be stored in the log in the order they were generated by the ECU, and the same goes for each of the other sources.
There is a chance that events from two different sources might be stored out of sequence.
Events are only written to the log after they are *completely* received to ensure that the bytes making up a single event can be written atomically to the log.
This means that in the time it takes to receive a large GPS report, the system might write one or more short ECU events while the GPS report is arriving, even if the GPS report started arriving before the ECU events.
This potential sequencing discrepancy is currently treated as unavoidable and inconsequential.
A decoder can treat a log file as though its events are stored in sequence.

**Note: Logs must be processed before they can be displayed, but the binary log as stored on the SD Card in the ECU is never modified.
Its data always remains as originally recorded.**

## Log Timestamps and Event Sequencing

Giving every ECU event a precise timestamp would take a lot of space, so only certain events get one.
For example, the ECU logs the precise time at which the crankshaft position sensor triggers, 6 times per revolution, or every 60 degrees.
These crankshaft events must be timestamped if the log is to be able to determine how fast the crankshaft was spinning over each 60 degree span.
In contrast, knowing *precisely* when the ECU measured things like its coolant temperature or the ambient air pressure is not important.

If the engine is rotating, precise crankshaft timestamps will appear at a relatively high rate in the log.
Knowing that a specific coolant temperature measurement was logged *sometime* between a pair of precisely timestamped crankshaft events is accurate enough for our purposes.

In short: while only certain events get timestamped, the log's guarantee of event sequencing means that untimestamped events will be sequenced correctly in relation to the timestamped events around them.

## Recreating Elapsed Time

The ECU measures time with a free-running 16-bit counter that ticks once every 2 microseconds.
Every timestamp in the log is a 16-bit value taken from that counter.
There are two reasons for that: the HC11's timer and input-capture registers are only 16 bits wide, so 16 bits is all the ECU can capture, and a 2-byte timestamp keeps the log small.

During normal operation the ECU's timer overflows every 131.072 milliseconds, or nearly 8 times per second.
The log decoder, in contrast, must track time over a much longer span, like rides that might last for many hours.
It tracks elapsed time as a 64-bit number of nanoseconds since the ECU booted.
To accurately convert 16-bit ECU time into 64-bit elapsed time, the decoder must detect every overflow of the ECU's timer as it reads the log events.

The crankshaft and camshaft events are the log's true timestamps.
Each carries a precise reading of the ECU's timer at the moment of the event, and each places the log on the clock: every untimestamped event located before it in the log must have happened before the timestamp time, and every one after it in the log must have happened after the timestamp time.
The problem for a decoder is that if the engine is running very slowly or stopped, there will be no timestamps in the log to see elapsed time advance.

To ensure proper elapsed time accounting under these circumstances, two other log events are required: timer overflow (OFLO) and timer half-overflow (HOFLO).

Even though these events are timer-related, the log decoder treats the OFLO and HOFLO events as *state* events, not precise timestamps.
Their existence guarantees that a decoder will detect every overflow even when the engine is not running:

* The timer **overflow** event (OFLO): the ECU has detected that bit 15 of the timer changed from '1' to '0'
* The timer **half-overflow** event (HOFLO): the ECU has detected that bit 15 of the timer changed from '0' to '1'

The decoder keeps track of the state of bit 15.
The first event encountered showing bit 15 change from '1' to '0' indicates a rollover.
That event can be a crankshaft or camshaft timestamp or the overflow event.
Whichever it is triggers the overflow accounting and sets the decoder's state of bit 15 to '0'.
Later events with bit 15 at '0' do nothing, because there is no change of state.

Similarly, the first event showing bit 15 change from '0' to '1' primes the decoder to see the next overflow.
Again, that event can be a timestamp or the half-overflow event.
It is quite possible for a crankshaft event to be processed after the timer's top bit goes from '0' to '1', but before the half-overflow event can be logged.
The crankshaft timestamp then primes the decoder, and the half-overflow event is redundant.

Together, the two events put a timer reading in the log roughly every 32,768 ticks (65 ms): the overflow event at the start of each timer period, and the half-overflow event in the middle.
A decoder must see the timer at least once in each half of the period to catch every change of state.
This mechanism detects all overflows whether the engine is running, stopped, or turning so slowly that the timer overflows between crankshaft events.
The decoder then computes elapsed time as (overflow count × 65536 + timer value) × 2000 nanoseconds.

### VTA Event Timing

Crankshaft timestamps give precise time only while the engine is turning, and they only come once per 60 degree subrotation.
To place the many untimestamped events more precisely, even with the engine stopped, the ECU also adds timer bits to the throttle position (VTA) event.

VTA is the ECU's most frequently converted analog input.
The HC11's A/D converter produces a 10-bit result, so the 16-bit VTA log value has 6 unused bits.
The ECU puts those 6 bits to work.
Each time it logs a VTA reading, it reads the timer, takes the 6 most significant bits of the 16-bit count (bits 15 to 10), and stores them in the unused top 6 bits of the VTA word.
The lower 10 bits hold the throttle reading as usual.
Interrupts are disabled while this happens, so a crank event cannot slip in between reading the timer and writing the log event.

Six bits of the timer divide each 131.072 ms timer period into 64 steps of 1024 ticks, which is 2.048 ms each.
A VTA event therefore says: *at the moment of this reading, the timer was somewhere in this 2.048 ms step*.
The decoder takes the start of the step as the time, so the true time is between 0 and 2.048 ms later than the decoded time.

This costs no extra log space, and it helps refine the timing for the many events that carry no timestamp, such as manifold pressure and coolant temperature.
Those events are sequenced against the VTA events around them, so their times are known to about 2 ms, even with the engine stopped.
Without VTA, the only anchors would be the overflow events, 131 ms apart (65 ms with the half-overflow event), which is 64 times (or 32 times) coarser.
The decoder also counts a wrap when it sees one in these timer bits, but the overflow mechanism described above does not depend on them.
